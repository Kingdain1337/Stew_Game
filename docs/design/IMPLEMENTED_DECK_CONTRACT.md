# Implemented deck contract (catalog v0.2, rules version 6)

This is the executable boundary today, not the full future architecture in [Deck Architecture](DECK_ARCHITECTURE.md). Start with the [points-engine thesis](POINTS_ENGINE_THESIS.md) and [authoring brief](DECK_AUTHORING_BRIEF.md) for why a deck should exist. Use `decks/culture/`, `decks/hearth/`, and `decks/chorus/` as concrete examples, then verify a new design with exact fixtures and human observation.

## Package and registration

A deck has `deck.json`, `rules.js`, and `presentation.js`. The JSON manifest defines its namespaced `id`, `schemaVersion: 1`, `openingIds`, `cards`, and `residues` (including tiers), plus display identity. Its rules module exports `resourceCaps`, `handlers`, and optional `reactionPlan`; its presentation module exports labels, accents, motion identity, and `eventText`. `decks/catalog.js` statically imports and registers the package, validates manifest references/basic numeric fields, and returns a catalog. New decks currently require editing that registry and the browser's deck-choice list; this is intentional trusted-code registration, not arbitrary runtime script loading. Add a test for every new mechanic.

The game always supplies Pantry. The playable setup chooses one themed deck, a pot, a story and a seed; the core still accepts two themes for cross-deck diagnostics and replay. Rules v6 starts with an empty pot and three seeded stock options; `chooseStock` adds one, then `startChapter` begins the encounter. Stories set their own chapter counts, arc boundaries, targets and boss locations: royal has ten five-bowl chapters, caravan has seven. Three offers, one add/discard decision, heat in 5°C steps (0–120°C), a portion choice, and one serving remain shared host rules.

Iron is 3 L with seven residue slots; Royal is 5 L with five. Small / standard / large use 0.2 / 0.4 / 0.7 L fractions, with ×0.65 / ×1 / ×1.5 bowl points. Ordinary retention is `1 - fraction / capacity`; printed standard retention protection and Extraction loss scale with fraction. Explicit ability costs do not. Below 0.15 presence, surviving volume joins fixed-property Broth with modest volume-scaled Power. No separate ingredient-place limit exists. See [current exact mechanics](STORIES_SERVINGS_V5.md).

Stories own narrative, preferences, boss parameters, targets and a story deck plus two recommended alternatives. The caravan story restricts its starting stocks and first-chapter offers to forage-friendly choices; its bandits require three scored ingredient types across their encounter. The host prepares seeded requests/curses/locked heat before input and enforces required portion/heat at commit. Foreign princess ingredients activate their owning deck's mechanics without extending the normal offer pool. `activeDeckIds` includes selected decks, live ingredient/residue owners and decks with banked resources.

Each residue defines `rarity`, its matching `maxTier` (Common 10, Uncommon 8, Rare 5, Ultra-rare 3), and `objective: {metric, target, text}`. Simple bonuses may use a declarative `effect` (`all`, `type`, `size`, or `heat`, with `perLevel`). Metrics come from the validated host registry in `residue-objectives.js`. Progress starts at installation, persists within a run, and upgrades immediately on reaching the target, carrying surplus through further levels. Silenced residues have effective tier zero and gain no progress. Reward offers are a seeded weighted draw of three uninstalled residues; full slots require explicit replacement. A new objective metric is an explicit host extension, not an arbitrary deck callback. See [rules v7](PROGRESSION_V7.md).

## Handler timing and input

`handlers.preServe(context)` runs after the chosen ingredient and heat are committed, before base score and reactions. All active decks run with Pantry first and the other deck IDs sorted. Host operations from one handler are applied before the next handler receives its frozen snapshot. Then `reactionPlan` determines the order and bonus multipliers of common original reactions, which resolve in that order, followed by deck-created original pulses. `handlers.derived(context)` sees all original pulses and may create derived pulses; derived pulses are not passed back as original pulses. After all scoring, the host applies customer, portion and fulfilled-request multipliers, records the breakdown and objective metrics, depletes ingredients, and advances objective progress. `handlers.encounterStart(context)` runs on `startChapter`, before first-bowl boss preparation, and may restore declared resources.

The handler input is `{ state, cards, residues, originalPulses }`. It is frozen and read-only. Use `packages/deck-contract/helpers.js` for effective properties, tagged-card lookup, residue tiers, and stable oldest selection. Do not mutate state, call `Math.random`, or read the DOM. Every intentional change is returned as an operation. A bad operation rejects the whole command and leaves the original state untouched.

| Operation | Allowed phase | Meaning |
| --- | --- | --- |
| `resource` | `preServe`, `encounterStart` | Change a resource declared in `resourceCaps`, within `[0, cap]`. |
| `flag` | `preServe`, `derived` | Set a numeric encounter-local flag; flags reset after reward. |
| `consume` | `preServe`, `derived` | Spend ingredient presence before score or after original pulses, respectively. |
| `retention` | `preServe` | Request a minimum presence fraction kept after the serving. |
| `pulse` | `preServe`, `derived` | Add per-ingredient score deltas. Pre-serve pulses are original and may explicitly be echoable; derived pulses cannot be echoed. |

Every operation needs a `sourceId` in its deck namespace (`deckId.name`), and targets must refer to current pot instance IDs. A pulse has `deltas: [{instanceId, amount}]`; derived pulses should carry `parentIds` from the original pulse events they copy. A pulse may also provide `participantIds` for all ingredients visually involved, including catalysts that receive no points. Those IDs are validated against current pot instances; if omitted, the host uses delta targets. A derived echo can reuse the original pulse's participants, while its own source card is highlighted separately. The host enforces numeric bounds and phases. The current validation is a small runtime guard, **not** a complete JSON Schema, static type contract, or security sandbox. Only reviewed local code should be registered.

## Scoring and feedback

`reactionPlan({state, cards, residues})` is a pure, frozen-snapshot query shared by UI inspection and scoring. It returns `{kind: 'lead', sourceId, reactionId}` to prioritize common chemistry, or `{kind: 'amplify', sourceId, reactionId, factor}` to multiply that reaction's bonus. Sources must belong to the deck namespace, reaction IDs must exist, and each factor must be between 1 and 10. Duplicate lead requests preserve the first request; otherwise priority follows deck order and each deck's operation order. Unprioritized reactions retain host order. Scoring queries the plan after pre-serve costs/resources, while an uncommitted pot inspection reflects its current state. Authoritative serve preview includes the chosen draft and those pre-serve changes. Original events carry the applied modifiers for attribution. The core validates operations, not whether a trusted deck invented sensible conditions.

The [v4 engine notes](DECK_REBALANCE_V4.md) explain the original Char bank/Overflow/Blaze and conductor sequences. Current level values, objectives and additional residue effects are in deck manifests and the [v5 specification](STORIES_SERVINGS_V5.md).

Base score is card power × current presence ÷ pot capacity × its heat-curve multiplier. Common reaction deltas use the running score, so the conducted reaction order can compound. Residues and Char can amplify a named reaction's delta through `reactionPlan`. Deck original and derived pulses add to that raw score. Customer, portion and fulfilled-request multipliers apply to the resulting ingredient totals; pantry residues now multiply named reaction bonuses, not the whole bowl. The explanation retains base, per-event contributions, multipliers, and final total. Each base contribution now emits `baseScored` before reaction pulses; both it and every pulse contribution reference the event ID. Each reaction pulse carries `participantIds` and optional `parentIds`, so the browser can show connectors, echoes, per-ingredient point bubbles and score-bar increments in exact event order. Presentation code interprets those events; it cannot change the authoritative score. Distinctive spectacle should show the actual source, cost, target, and resulting score, with a readable ledger and speed/skip controls.

The web client resolves card and residue art by explicit `imageId` when present, otherwise by ID: `assets/ingredients/<imageId-or-cardId>.png` and `assets/residues/<imageId-or-residueId>.png`. Stock definitions and new residues deliberately alias existing illustrations. Pot art is `assets/pots/<potId>.png`; chapter portraits are `assets/characters/<portrait>.png`. The ingredient art is reused as card illustration, pot sprite and content-row icon. The pot's bouncing, buoyancy and bubbling are visual-only and do not affect rule resolution.

For reproducibility, `createGame(catalog, options)` creates a run; `step(catalog, state, command)` returns a new state/events/errors; `preview` uses that reducer without changing the live state; and `replayGame` applies a recorded `commandLog` to the same seed, story, pot, deck set, catalog, and rules version. Replay commands include stock and chapter setup as well as servings and rewards. Persisted-save migration, package hashing, a content studio, and Unity parity are not implemented yet.

## Minimum acceptance for another example deck

Write a one-sentence engine identity, at least three state-dependent choice scenarios, a precise cost and cap, one run-residue decision, and visual event language. Give it a straightforward line and a less-obvious second-order interaction with a common reaction or another deck. Add deterministic tests for a normal trigger, unavailable cost, cap/reset, residue effect, and mixed-deck interaction. Run bot diagnostics to catch impossible or dominant lines, then conduct human playtests before calling the deck fun or balanced.
